*Проект realhelpdesk · черновик технического предложения (RFC)*

> **Статус: реализовано** (ветка `feat/captcha-docs`, коммиты `af9da33` →

## 1. Краткое резюме

Текущая капча (картинка с 5 символами, in-memory хранилище, `capId` от клиента) защищает от примитивных ботов, но:

- **не держит современный OCR/ML** и мультимодальные модели: искажённый текст на светлом градиенте сегментируется и распознаётся автоматически;
- **плохо масштабируется** (статическая `ConcurrentHashMap` в JVM, нет реплик);
- **имеет архитектурные уязвимости** (клиентский `capId`, O(n)-очистка при каждой записи);
- **неудобна и недоступна** для людей (нет аудио/альтернативы, мобильный ввод, WCAG).

**Предложение:** отказаться от «одной картинки на всех» и перейти на *многоуровневую* схему:

1. **Базовый уровень (для всех, без действий пользователя)** — серверный подписанный challenge + Proof-of-Work в браузере + honeypot/тайминг.
2. **Эскалация (только при подозрительном поведении)** — интерактивное задание «выбери эмодзи/иконку».
3. **Опционально** — подключаемый внешний провайдер (Cloudflare Turnstile / Yandex SmartCaptcha / hCaptcha) через единый интерфейс.

Идея с выбором смайликов хороша **как UX-уровень эскалации**, но сама по себе не повышает защиту от современных ботов (см. раздел 3).

## 2. Анализ текущей реализации

### 2.1. Стойкость к автоматическому решению

| Аспект | Наблюдение | Риск |
| --- | --- | --- |
| Тип задачи | Распознавание 5 символов из алфавита в 31 знак | CNN-решатели и vision-LLM решают такие капчи с высокой точностью за доли секунды и копейки |
| Контраст | Белый текст на светло-голубом градиенте, один шрифт, фиксированный размер 42 px | Легко бинаризуется и сегментируется; нет шума, линий, перекрытий |
| Искажения | Поворот ±14°, сдвиг ±4 px, волна 2 px | Слабые: символы остаются раздельными и узнаваемыми |
| Ограничение алфавита | Исключены неоднозначные символы | Хорошо для людей, но уменьшает пространство для решателя |
| Цена атаки | Решение одной картинки = одна регистрация | Нет «стоимости» для атакующего, кроме рейт-лимита по IP, который обходится ротацией IP |

Вывод: капча отсекает только скрипты без OCR. Против целевой атаки (массовые регистрации, спам кодами на email) это не барьер.

### 2.2. Архитектурные и безопасностные замечания

1. **`capId` выбирает клиент.** Любой может запросить картинку с чужим `capId` (он короткий, ≤ 10 символов, часто «кусок UUID») и перезаписать код жертвы → жертва получает «Провал капчи». Это точка для целевого DoS и подмены. Также `capId` не привязан к действию (register / email-code) и к клиенту.
2. **Статическая in-memory карта.** Нет горизонтального масштабирования, рестарт сбрасывает капчи. Нет верхней границы размера: с ротацией IP (30 запросов/60 с на каждый) за 5 минут TTL карта растёт неограниченно.
3. **`purgeExpired()` при каждом `put`** — полный проход по карте; под нагрузкой это O(n) на каждый запрос выдачи и дополнительный вектор DoS по CPU.
4. **Нет привязки результата к операции.** Проверка — одноразовая, но «решённая капча» не превращается в токен, подписанный под конкретное действие.
5. **Нет адаптивности.** Одинаковая сложность для всех: и для первой попытки обычного человека, и для 50-й попытки подозрительного клиента.
6. **Нет сигналов поведения:** honeypot-поле, время заполнения формы, повторные провалы с одного IP/подсети не влияют на сложность.
7. **Метрики есть, но без разреза по причине провала** (истёк TTL / неверный код / неизвестный `capId`) — трудно отличить жалобы пользователей от атаки.

### 2.3. UX и доступность

- Нет аудио- или иной альтернативы (WCAG 1.1.1, 3.3.8 «Accessible Authentication»).
- Ввод 5 символов с искажением на мобильном — частая причина отказа от регистрации; ошибка требует повторной выдачи картинки.
- Регистронезависимость — хорошо, но визуальная двусмысленность остаётся (напр. `S/5`, `V/U`).

### 2.4. Что сделано хорошо (сохранить)

- Одноразовость кода (`remove`) и короткий TTL.
- Проверка *до* бизнес-логики.
- Обязательность включения в проде через `ProdPreflightValidator`.
- Метрика `auth.attempts{type="captcha"}`, отсутствие ПДн в хранилище.
- Подробные тесты и изоляция биндинга свойств.

## 3. Варианты решения

### Вариант A. Внешний провайдер (Turnstile, SmartCaptcha, hCaptcha, reCAPTCHA)

| Плюсы | Минусы |
| --- | --- |
| Поддерживаются командами, обновляются под новые атаки | Зависимость от внешнего сервиса и его доступности |
| Risk-анализ и сигналы устройства «из коробки» | Передача сетевых данных третьей стороне: вопросы приватности и локализации ПДн (для российской аудитории важна проверка по 152-ФЗ) |
| Минимум своего кода | Блокировки/доступность в отдельных регионах (у каждого провайдера свои) |
| Невидимый режим для большинства пользователей | Вендор-лок, настройка CSP, возможные платные тарифы |

Подходит как **внешний слой или fallback**, особенно если данные пользователей не должны покидать страну: тогда смотреть в сторону Yandex SmartCaptcha.

### Вариант B. Собственный Proof-of-Work (в духе ALTCHA / Cap.js / mCaptcha)

Сервер выдаёт подписанный challenge, клиент в браузере подбирает `nonce` так, чтобы хэш имел N ведущих нулевых бит. Пользователь ничего не вводит.

| Плюсы | Минусы |
| --- | --- |
| Нулевое трение и полная доступность | Не отличает человека от бота: повышает *стоимость* массовых действий, а не блокирует |
| Self-hosted, нет передачи данных третьим лицам | Слабые устройства решают медленнее (нужна адаптивная сложность) |
| Лёгкая реализация (HMAC + SHA-256), без хранения состояния | Нужен JS-виджет на клиенте (WebCrypto, Web Worker) |
| Сложность регулируется по риску | Не защищает от атакующего с вычислительным ресурсом при низкой сложности |

### Вариант C. Интерактивная задача «выбери эмодзи/иконку»

Пример: «Выберите самолёт» + сетка из 6–9 картинок; или «Нажмите иконки в порядке: 🐱 → 🚗 → 🍎».

| Плюсы | Минусы |
| --- | --- |
| Быстрее и приятнее, чем ввод искажённого текста | Маленький словарь картинок → CLIP/vision-модели решают практически без ошибок |
| Нет проблем с неоднозначными буквами | Эмодзи по-разному выглядят на платформах; Java2D плохо рисует цветные эмодзи |
| Хорошо ложится на мобильные | Нужна локализация подписей и текстовые альтернативы для скринридеров |
| Показывать можно только при подозрении | Лицензии на наборы иконок (например, Twemoji — CC-BY 4.0, нужна атрибуция) |

Честный вывод: **с точки зрения защиты от ИИ сетка эмодзи ≈ текстовая капча**; её ценность — UX и возможность усиливать за счёт случайных трансформаций, шума и динамической комбинации заданий. Поэтому используем её как *второй уровень*, а не единственный барьер.

### Вариант D. Поведенческие сигналы (honeypot, тайминг, репутация)

Скрытое поле-ловушка, минимальное время заполнения формы (напр. ≥ 2–3 с), счётчик провалов по IP/подсети/email-домену. Почти бесплатно, отсекает значительную долю тупых ботов, но сам по себе недостаточен.

### Сравнение

| Критерий | Текущая | A. Провайдер | B. PoW | C. Эмодзи | D. Поведение |
| --- | --- | --- | --- | --- | --- |
| Защита от современных ботов | Низкая | Высокая | Средняя (экономическая) | Низкая–средняя | Низкая |
| Трение для пользователя | Высокое | Низкое | Нет | Среднее | Нет |
| Доступность | Плохая | Хорошая | Отличная | Средняя | Отличная |
| Приватность / независимость | Полная | Зависит от вендора | Полная | Полная | Полная |
| Стоимость внедрения | — | Низкая | Средняя | Средняя–высокая | Низкая |
| Масштабирование | Одна JVM | Внешнее | Stateless | Stateless (с подписью) | Нужен счётчик |

## 4. Рекомендуемое решение: многоуровневая капча

```
Клиент ──► POST /api/v1/captcha/challenge {action}
          ◄── {challengeId, type, params, expiresAt}

Уровень 1 (по умолчанию): type = "pow"
  клиент считает nonce в Web Worker, пользователь ничего не делает

Уровень 2 (при риске): type = "emoji"
  клиент показывает задание, пользователь выбирает ответ

Клиент ──► POST /api/v1/auth/register  (поле captchaToken)
          POST /api/v1/email/codes    (заголовок X-Captcha-Token)
```

### 4.1. Принципы

1. **Challenge выдаёт только сервер.** Клиентский `capId` убирается. Идентификатор — 128-битный случайный, внутри подписанного токена.
2. **Stateless-подпись.** Challenge содержит `{id, action, difficulty, exp, [answerHash]}` и HMAC-SHA256 серверным секретом. Хранить ответы не нужно.
3. **Привязка к действию.** Токен для `register` не принимается на `email-code` и наоборот.
4. **Одноразовость.** В хранилище попадает только `id` использованных токенов (Caffeine с `maximumSize` и `expireAfterWrite` для одной инстанции, Redis при масштабировании).
5. **Адаптивная сложность.** Уровень и сложность зависят от риска: число провалов/запросов с IP и подсети, срабатывание рейт-лимита, honeypot, слишком быстрая отправка формы.
6. **Единый интерфейс** `CaptchaVerifier` с реализациями `LegacyTextVerifier`, `PowVerifier`, `EmojiVerifier`, `ProviderVerifier` и переключателем `captcha.mode`.

### 4.2. Уровень 1 — Proof-of-Work

- Сервер выдаёт `salt` (случайный), `difficulty` (число ведущих нулевых бит), `exp`, подпись.
- Клиент ищет `nonce`, при котором `SHA-256(salt || nonce)` имеет ≥ `difficulty` нулевых бит; вычисления в Web Worker, чтобы не блокировать UI.
- Сервер проверяет подпись, срок, хэш и отсутствие повторного использования.
- Стартовая сложность: порядка 18–20 бит (2^18–2^20 попыток; ориентир — доли секунды–пара секунд на среднем телефоне). Значение нужно откалибровать замерами на реальных устройствах.
- При росте риска сложность поднимается ступенями, а затем включается уровень 2.

### 4.3. Уровень 2 — выбор эмодзи/иконок

- Сервер собирает сетку 3×3 (или 2×3) из набора заранее подготовленных PNG/SVG (не из системного шрифта, чтобы не зависеть от платформы и не бороться с цветными эмодзи в Java2D).
- Для каждой иконки — случайные масштаб, поворот ±20°, смещение, фоновый шум; перемешанный порядок.
- Задание: «Выберите все иконки с категорией X» или «Выберите X». Категорий десятки, комбинируются случайно; ответ — индексы ячеек.
- Хэш правильного ответа кладётся в подписанный токен (`HMAC(answer || id)`), так что сервер ничего не хранит.
- Доступность: текст задания в HTML (не в картинке), у ячеек `aria-label` не раскрывает ответ, но есть кнопка «Другое задание» и путь через email/поддержку либо внешний провайдер для пользователей, которым интерактивное задание недоступно.
- Для усиления: ротация набора иконок, регулярное добавление новых категорий, контроль доли успешных прохождений по метрикам.

### 4.4. Дополнительные сигналы

- Honeypot-поле (скрытое, должно остаться пустым).
- Минимальное время между выдачей challenge и отправкой формы.
- Счётчик провалов по IP / подсети /24 / домену email.
- Привязка к IP **не жёсткая** (мобильные сети меняют адрес), только как сигнал риска.

### 4.5. Контракт API (черновик)

| Эндпоинт | Было | Станет |
| --- | --- | --- |
| Получение задания | `GET /api/v1/captcha?capId=...` → JPEG | `POST /api/v1/captcha/challenge` `{action: "register"\|"email-code"}` → JSON c `challengeId`, `type`, `params`, `expiresAt` |
| Ответ на задание (уровень 2) | — | `POST /api/v1/captcha/solve` `{challengeId, answer}` → `{captchaToken}` |
| Регистрация | `?capId=` + `capCode` в теле | `captchaToken` в теле `RegisterRequest` |
| Код подтверждения email | `?capId=&capCode=` | заголовок `X-Captcha-Token` |
| Ошибка | `400`, «Провал прохождения капчи» | `400` с `code` причины: `expired`, `invalid`, `replayed`, `wrong_action`; `429` при лимите |

Для PoW клиент сразу после вычисления получает `captchaToken` тем же `solve`-вызовом (передаёт `nonce`).

## 5. План внедрения

**Этап 0. Быстрые исправления текущей капчи (1–2 дня, независимо от остального)**

- Серверная генерация `capId` (128-бит), привязка записи к действию.
- Заменить статическую карту на Caffeine (`maximumSize`, `expireAfterWrite`), убрать `purgeExpired()` при каждом `put`.
- Добавить в метрику тег причины провала.
- Повысить контраст и добавить шум/линии, если легаси остаётся на переходный период.

**Этап 1. Каркас (3–5 дней)**

- Интерфейс `CaptchaVerifier`, `captcha.mode = legacy | pow | pow+emoji | provider`.
- Подписанные токены (HMAC), хранилище использованных `id`.
- `ProdPreflightValidator`: запрет `mode=off` в проде, проверка длины и наличия секрета.

**Этап 2. PoW + honeypot + тайминг (1 неделя)**

- Серверная часть, клиентский виджет (Web Worker), тесты и калибровка сложности.
- Включить для `register` и `email-code`, легаси оставить как fallback за флагом.

**Этап 3. Эмодзи-уровень и адаптивность (1–2 недели)**

- Рендер сетки, набор иконок и категорий, проверка лицензий.
- Сервис оценки риска и правила эскалации.

**Этап 4. Удаление легаси**

- После периода наблюдения (2–4 недели по метрикам) удалить `CaptchaGenerator`, `CaptchaStorage`, `GET /api/v1/captcha`, обновить `docs/api.md`, README и этот документ.

## 6. Тестирование и метрики

**Тесты:** подпись и срок challenge, подмена `action`, повторное использование токена, неверный PoW, граничные значения сложности, детерминированный рендер сетки с фиксированным `seed`, нагрузочный тест выдачи (проверка отсутствия роста памяти).

**Метрики:**

- `captcha.challenge.issued{type}`;
- `captcha.verification{type, result, reason}`;
- время решения PoW (с клиента, опционально) и доля эскалаций на уровень 2;
- конверсия формы регистрации до/после (чтобы поймать ухудшение UX);
- доля регистраций, не подтвердивших email (косвенный индикатор ботов).

## 7. Риски и компромиссы

| Риск | Митигация |
| --- | --- |
| PoW замедляет слабые устройства | Адаптивная сложность, замеры на реальных устройствах, таймаут с переходом на уровень 2 |
| Решатели эмодзи-заданий на базе vision-моделей | Эмодзи только как эскалация; сочетание с PoW, рейт-лимитами и репутацией; опционально внешний провайдер |
| Компрометация секрета HMAC | Ротация ключей (поддержка двух активных ключей), хранение вне репозитория |
| Рост сложности кода | Единый интерфейс, поэтапное включение за флагами |
| Лицензии иконок | Выбор набора с разрешающей лицензией, страница атрибуции |
| Нужна вторая инстанция приложения | Redis для множества использованных `id` (всё остальное stateless) |

## 8. Открытые вопросы

1. Допустима ли передача данных внешнему провайдеру (требования по локализации ПДн)? От ответа зависит, нужен ли вариант A.
2. Планируются ли несколько инстансов приложения в ближайшее время (нужен ли Redis уже на этапе 1)?
3. Есть ли мобильные нативные клиенты, для которых нужен нативный PoW-решатель вместо JS?
4. Какие допустимые потери конверсии на регистрации и целевое время прохождения (задаёт сложность PoW)?
5. Нужна ли аудио- или иная альтернатива по требованиям доступности для вашей аудитории?

## 9. Итоговая рекомендация

1. Сразу выполнить **этап 0** — он закрывает реальные уязвимости текущей реализации.
2. Внедрить **PoW + honeypot + тайминг** как невидимый базовый уровень.
3. Добавить **выбор эмодзи** как интерактивную эскалацию для подозрительных клиентов.
4. Заложить интерфейс провайдера, чтобы при необходимости подключить Turnstile или SmartCaptcha без переписывания бизнес-логики.
