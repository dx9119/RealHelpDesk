# n1.md — проблема N+1: где она есть и где может появиться

Аудит `src/main`: 12 репозиториев (15 файлов), 7 MapStruct-мапперов, сервисы репозиторного слоя.
Проверялось: как грузятся связи (`FetchType`, `@EntityGraph`, `JOIN FETCH`), есть ли циклы с обращениями к БД, и что происходит при маппинге страниц.

> **Ревизия 3 (реализация).** Пункты **#1–#13 закрыты** в коде; регрессия закрыта тестом `NPlus1GuardTest` (§5, §6). Отклонения от исходных рекомендаций:
> - **#5/#7: EAGER сохранён, добавлен `@BatchSize(size = 50)`** вместо перехода на LAZY. Причина: `getAllowedUserIds()` читается в 15 точках, часть **вне транзакции** (`AccessValidationService`, `TicketAccessValidationService`, `EmailDeliveryService`, `NotificationPublisher`, `getPortalSettings`) — LAZY дал бы `LazyInitializationException` без OSIV. Батч даёт тот же выигрыш `1 + ⌈N/50⌉`; гипотеза проверена guard-тестом (список из 20 порталов — ≤2 запроса);
> - **#1: на каждый портал своя транзакция через `TransactionTemplate`** (не «одна транзакция на весь батч»): сбой одного портала не откатывает остальные; оповещения и письма уходят **после коммита всех удалений**; `NotificationPublisher.publishToUsers`/`publishToPortalUsers` получили `@Transactional` (публикация возможна уже вне транзакции удаления);
> - **#13: `LAZY` + `@BatchSize(50)`** — реализовано как рекомендовано; единственный читатель коллекции `SecurityUser.getLatestJwtRefreshToken` — мёртвый код (вызовов нет);
> - **#9/#10: один bulk-`UPDATE`** `updateStatusByEmailAndStatus` + публичный `GetTokenService.revokeActiveRefreshTokens(user, nextStatus)`; метод `getActiveRefreshTokens` и зависимость `SaveTokenService` в `UserManageService` удалены как ставшие ненужными;
> - **#3: фолдаут переписан на батчи** — `getUsersByIds` + `muteEventsByEmails` + чистая `isMuted`; `EmailLog` пишется пачкой (`EmailLogService.addAll`); лимитер (`RECOVERY_PASSWORD`) остался в одиночном `sendEmail`;
> - **#4/#6: проекция `findProjectedByIdIn`** + `UserDomainService.getUserDetailsByIds` → `Map<Long, UserDetailsProjection>`; заглушка «Пользователь не существует» — по отсутствию ключа;
> - **#2: граф подхватился** — переопределённый `findAll(Specification, Pageable)` с `@EntityGraph` работает (проверено guard-тестом: страница тикетов ≤3 запроса, доступ к `author`/`portal` допросов не добавляет).
>
> Итог: 464 теста зелёные, `spotless:check` чистый. Открытых пунктов по N+1 нет; #8 и #11 — замечания на будущее, как и было.

## 4. Рецепты

**1) Батч вместо N точечных выборок (лечит #3, #4, #6):**

```java
Set<Long> ids = ...;
Map<Long, UserModel> users = userRepository.findAllById(ids).stream()
        .collect(Collectors.toMap(UserModel::getId, Function.identity()));
// далее подстановка из мапы, а не запрос в цикле
```

Пока `UserModel.jwtTokenRefresh` остаётся EAGER (#13), такой батч по пользователям добавит ещё по одному `select` на пользователя — выигрыш от `findAllById` раскроется только в паре с #13. Для #4 и #6, где грузятся проекции `UserDetailsProjection`, батч работает и без #13.

**2) EAGER-коллекция → LAZY + батч (лечит #5, #7, #13):**

```java
@ElementCollection(fetch = FetchType.LAZY)
@BatchSize(size = 50)
@CollectionTable(name = "portal_access", joinColumns = @JoinColumn(name = "portal_id"))
@Column(name = "allowed_user_id")
private Set<Long> allowedUserIds;
```

При `@BatchSize(50)` страница из 100 порталов даёт `1 + 2` запроса вместо `101`. Глобальная альтернатива без правки сущностей — `spring.jpa.properties.hibernate.default_batch_fetch_size=50`. Для `UserModel.jwtTokenRefresh` (#13) и `UserNotificationPreferencesModel.enabledEvents` (#7) — та же схема: `@OneToMany(fetch = LAZY)` / `@ElementCollection(fetch = LAZY)` плюс `@BatchSize`.

**3) Граф для поиска через `Specification` (лечит #2):**

```java
// в TicketRepository: переопределяем метод из JpaSpecificationExecutor и вешаем граф
@Override
@EntityGraph(attributePaths = {"author", "portal", "assignedUser"})
Page<TicketModel> findAll(Specification<TicketModel> spec, Pageable pageable);
```

Если граф на спецификации не подхватится в вашей версии Spring Data — рабочий запасной вариант: сначала страница id, затем гидрация одним `findByIdInAndTicketLiveStatus` (у него граф уже есть).

**4) Bulk-обновление вместо цикла (лечит #9, #10):**

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update RefreshTokenModel t set t.status = :next where t.user.email = :email and t.status = :current")
int updateStatusByEmail(@Param("email") String email, @Param("current") TokenStatus current, @Param("next") TokenStatus next);
```

**5) Убрать `parallelStream` с JPA (лечит #1):** `EntityManager` привязан к потоку; параллельная обработка внутри одной `@Transactional` — это не ускорение, а гонка. Достаточно последовательного цикла, а рассылку писем и публикацию оповещений стоит вынести за границу транзакции удаления.
